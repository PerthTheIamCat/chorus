# Security checklist สำหรับ Chorus รุ่นแจกผู้ใช้ทั่วไป

ตรวจเอกสารหลักเมื่อ 2026-10-12 — เอกสารนี้เป็นเกณฑ์และแผนตรวจ ไม่ใช่ผล audit โค้ดหรือคำรับรองว่าผ่าน ความต้องการคือครอบคลุมทุกฟีเจอร์ โดยแยกค่าเริ่มต้นกับเมื่อเปิด remote pairing/local AI

## วิธีใช้และหลักฐาน

ทุกข้อเริ่มเป็น **ยังไม่ตรวจ** บันทึก commit, release artifact/hash, macOS/architecture, feature flags, test fixture, expected/actual และหลักฐานที่ลบข้อมูลลับแล้ว กำหนดผลเป็น ผ่าน / ไม่ผ่าน / ยังไม่ตรวจ / ไม่เกี่ยวข้องพร้อมเหตุผล ห้ามนับว่าไม่มีปัญหาเพียงเพราะยังไม่มี reproduction

`P` = ข้อกำหนดแพลตฟอร์มตามช่องทางแจก, `H` = hardening ที่เสนอ, `T` = application-specific test ที่เสนอ ตัวเลข/นโยบายทดสอบด้านล่างเป็นข้อเสนอของการตรวจ ไม่ใช่ข้อบังคับของ Apple

## Checklist และวิธีพิสูจน์

| ประเภท | สิ่งที่ต้องตรวจ | วิธีตรวจและหลักฐานขั้นต่ำ |
|---|---|---|
| P | แจกโดย Developer ID: signing ของ executable/helper ทุกตัว, Hardened Runtime, secure timestamp, ไม่มี `get-task-allow=true`; notarization | ตรวจ release bundle จริงด้วย `codesign --verify --deep --strict --verbose=2 <app>` และ `codesign -d --entitlements :- <app>`; เก็บ notary log, `xcrun stapler validate <app>` และผลเปิดไฟล์ที่ดาวน์โหลดผ่าน Gatekeeper บนเครื่องสะอาด/บัญชีใหม่ การ notarize ไม่ทดแทน audit [Apple notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution) |
| P/H | ถ้าเลือก Mac App Store ต้องมี App Sandbox; สำหรับแจกตรงเป็น hardening ที่ต้องประเมินความเข้ากันได้ | บันทึกช่องทางแจกและ entitlements พร้อมเหตุผล ตรวจสิทธิ์ที่ process ลูกได้รับจริงและกรณีปฏิเสธไฟล์/เครือข่าย ห้ามสรุปว่า Hardened Runtime เท่ากับ sandbox [Apple App Sandbox](https://developer.apple.com/documentation/xcode/configuring-the-macos-app-sandbox) |
| H/T | agent execution และ permission mediation ต้องบังคับที่จุดเรียกเครื่องมือ ไม่พึ่งคำสั่งใน prompt | ทดสอบ read/write/exec/network ผ่าน UI, daemon, MCP และ retry โดยไม่อนุญาต/ปฏิเสธ/ยกเลิก; เปลี่ยน arguments, cwd, symlink หลังอนุมัติแล้วต้องไม่ขยายสิทธิ์โดยเงียบ; approval ต้องแสดงผลกระทบจริงและผูกกับ operation นั้น [OWASP excessive agency](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/) |
| H/T | repository, tool descriptions/results, เอกสาร และข้อความจาก agent อื่นเป็นข้อมูลไม่น่าเชื่อถือ | ใส่ fixture ที่สั่งอ่าน secret, ส่งข้อมูลออก หรือเปลี่ยน permission; เก็บ trace ว่าข้อมูลไม่กลายเป็นอำนาจอนุมัติ การเปิด repo หรือเพิ่ม MCP server ต้องไม่รัน executable/hook โดยผู้ใช้ไม่รับรู้; ตรวจ server binary, arguments และ environment ที่อนุญาต [OWASP excessive agency](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/), [MCP security](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices) |
| H/T | local daemon: จำกัด listener และป้องกัน browser/remote เรียกงานโดยไม่ได้รับสิทธิ์ | ทำตารางทุก route ว่าอ่าน/เขียน/เรียกคำสั่งอะไรและ auth ใด; ตรวจ IPv4/IPv6, Host/Origin ผิด, cross-origin browser request, ไม่มี/ผิด token, malformed body และขนาดเกินเพดาน ทุกทางต้องตรวจ auth ก่อน side effect; loopback เพียงอย่างเดียวไม่ใช่ authentication [MCP security](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices) เป็นแนวอ้างอิง ไม่ใช่ข้อบังคับกับ daemon ที่ไม่ใช่ MCP |
| H/T | remote pairing: user intent, authenticated encrypted transport, code อายุสั้น/ครั้งเดียว, จำกัดการเดา, revoke ได้ | fixture ทดสอบหมดอายุ, ใช้ซ้ำ, การแข่ง redeem, session ที่ revoke แล้ว, reconnect/restart, peer ผิด และการเปลี่ยน scope; กำหนด TTL/attempt budget จาก threat model ก่อนตัดสินผ่าน ไม่ฝัง bearer token ใน URL/log [OWASP authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html), [MCP security](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices) |
| H/T | secrets/Keychain: จำกัดสิทธิ์อ่านและการส่งต่อ; history/log/crash/export ต้องไม่รั่ว | ใช้ fake canary credential ในบัญชีทดสอบ ตรวจ create/read/delete/logout และ process ลูก; ตรวจไฟล์/diagnostic ที่สร้างจาก fixture ว่าไม่มี canary; ทดสอบ Keychain locked/denied แล้วไม่ fallback เป็น plaintext OAuth token ต้องตรง audience และไม่ passthrough ถ้าใช้ MCP authorization [Apple Keychain](https://developer.apple.com/documentation/security/keychain-services), [MCP security](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices) |
| H/T | previews: แยก untrusted HTML/Markdown จาก native bridge และสิทธิ์ไฟล์ | ทดสอบ script/event handlers, `javascript:`/`file:` URL, navigation/redirect, embedded remote image และ bridge messages; ต้องไม่อ่านไฟล์ เรียก native action หรือส่งข้อมูลออกโดยไม่ผ่าน policy ใช้ sanitization ตามบริบท; CSP เป็นชั้นเสริม [OWASP XSS](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet) |
| H/T | model/download/import: provenance, integrity, path และ resource budget | ทดสอบ digest ไม่ตรง, redirect ไปปลายทางต้องห้าม, truncated/resumed download, archive traversal/symlink และข้อมูลใหญ่เกิน; ยืนยันก่อน promote artifact, cleanup partial download และไม่ execute model metadata กำหนดเพดาน disk/RAM/time รวมหลังแตกไฟล์ด้วย [OWASP file handling](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html) ใช้เป็นแนวทางกับการรับไฟล์ |
| H/T | updates: ยืนยัน artifact ก่อนติดตั้งและปฏิเสธสิ่งถูกแก้ไข | ตรวจ updater ที่ใช้จริง; ทดสอบ signature ผิด/หาย, payload เปลี่ยน, update ขาดช่วง และนโยบาย downgrade หากใช้ Sparkle ตรวจ EdDSA และข้อกำหนดของเวอร์ชันที่ pin; ไม่เสนอเพิ่ม dependency โดยอัตโนมัติ [Sparkle](https://sparkle-project.org/documentation/) |
| H/T | dependencies และ release inventory: ตรวจ Rust/Swift/JS รวม binary ที่ bundle | เก็บ lockfiles, toolchain และรายการ shipped components; ตรวจ Cargo.lock ด้วย cargo-audit/RustSec ที่อัปเดต พร้อมวันที่ฐาน advisory; ตรวจ advisory ของ dependency ecosystem อื่น/ผู้ผลิตโดยตรง แยก vulnerability, unmaintained warning และ reachability; scan สะอาดไม่พิสูจน์ว่าไม่มีช่องโหว่ [RustSec](https://rustsec.org/) |

## เกณฑ์จัดลำดับงานที่เสนอ

- **ก่อน public release:** ต้องมีหลักฐานสำหรับเส้นทางที่นำไปสู่ arbitrary execution/write, secret exfiltration, auth/approval bypass และ update tampering; ถ้ายังไม่ตรวจให้คงสถานะไม่ทราบ ไม่ปิด finding ด้วยการอ้างว่าฟีเจอร์ปิดตามค่าเริ่มต้น
- **เมื่อเปิดฟีเจอร์:** remote access, MCP, downloads และ preview ต้องมี acceptance cases ของตนเอง ถ้าจะลดขอบเขตรุ่นแรกต้องตัดสินใจปิด/ไม่แจกเส้นทางนั้นจริงพร้อมพิสูจน์ผล
- **finding ที่นำไปแก้ไขได้:** ระบุ entry point → trust boundary → operation ที่เกิด → ผลกระทบ → เงื่อนไข exploit → หลักฐาน → แนวแก้เฉพาะจุด → regression test หลีกเลี่ยงให้คะแนนจากชื่อ API หรือ grep เพียงอย่างเดียว

ยังต้องตัดสินช่องทางแจก, supported macOS, ขอบเขตสิทธิ์ remote, retention/export ของข้อมูล และเพดาน resources ใน ticket ถัดไป เอกสารนี้ไม่เปลี่ยน source, signing, permission หรือ dependencies
