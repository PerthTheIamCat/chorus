# Attachment compatibility findings

## Current Chorus path

The current composer is a `TextEditor` over `DraftBox.text`; its `@` popup inserts a path/name into that text, and there is no picker/drop target or attachment model ([`Composer.swift`](../../../apps/macos/Sources/Chorus/Composer.swift#L3-L5), [#L73-L125](../../../apps/macos/Sources/Chorus/Composer.swift#L73-L125)). `Engine.send` accepts a `String` and calls `chorus_run_turn` with one C string ([`Engine.swift`](../../../apps/macos/Sources/Chorus/Engine.swift#L313-L329); [`chorus-ffi/src/lib.rs`](../../../crates/chorus-ffi/src/lib.rs#L152-L170)). Rust records only `user_text` as the message event, assembles prior turns into a textual prompt, and passes `&str` to the bridge ([`session.rs`](../../../crates/chorus-cli/src/session.rs#L545-L574)). The ACP adapter serializes exactly one `{type:"text", text}` content block ([`codex.rs`](../../../crates/chorus-acp/src/codex.rs#L322-L336)). Thus neither images nor binary files are currently sent as structured inputs.

The core blob store can hash, compress, and retrieve arbitrary bytes, but current turn submission does not call it for attachments. Ledger blob indirection is currently used for oversized event-body text; it is not an attachment store or message-to-attachment association ([`blob.rs`](../../../crates/chorus-core/src/blob.rs#L17-L47); `ledger::append` stores oversized `e.body` bytes). `@file` is a workspace path reference, not an uploaded-file transfer mechanism. Since session history is reconstructed into text, binary content cannot currently follow a handoff.

Not currently exercised by Chorus with attachments. |

ACP's v1 contract says agents must accept text and resource-link blocks, while image blocks require `promptCapabilities.image`; embedded `resource` content requires `embeddedContext`. Image bytes are base64 plus MIME type. The v1 protocol does not define a universal attachment byte/pixel limit ([ACP content spec](https://agentclientprotocol.com/protocol/content), [prompt capabilities](https://agentclientprotocol.com/protocol/prompt-capabilities)). This is a bridge handshake contract, not a guarantee that every chosen model/account tier accepts every attachment.

## File types and documented provider limits

- **Images:** Direct provider API references support common raster formats, but not uniformly. OpenAI's image-input interface accepts a URL/data URL or uploaded file ID and requires a vision-capable model ([Responses API input items](https://platform.openai.com/docs/api-reference/responses)). Anthropic lists JPEG, PNG, GIF and WebP; rejects images above 8000×8000 px and documents a maximum of 100 images per API request (and resizing behavior) ([Claude vision](https://docs.anthropic.com/en/docs/build-with-claude/vision)). Gemini lists PNG, JPEG, WebP, HEIC and HEIF; inline request payload is limited to 20 MB and larger inputs use Files API; it documents up to 3,600 images/request ([Gemini image understanding](https://ai.google.dev/gemini-api/docs/image-understanding)). These API-level limits must not be presented as verified ACP/CLI bridge limits.
- **PDF/common documents:** Gemini directly documents PDF support up to 50 MB or 1,000 pages ([document processing](https://ai.google.dev/gemini-api/docs/document-processing)). Anthropic's Messages API supports PDF/document processing, but the size/transport path differs from the Claude Code ACP adapter ([PDF support](https://docs.anthropic.com/en/docs/build-with-claude/pdf-support)). OpenAI's Responses API has `input_file` with file data, file ID, or URL ([API reference](https://platform.openai.com/docs/api-reference/responses)); support and limits vary by endpoint/model. Chorus currently provides no extraction or upload path for PDF, Office docs, archives, spreadsheets, etc.
- **Text files:** Existing `@` mention can only place a workspace path in text. A future feature can send text file content as embedded `resource` when the bridge advertises `embeddedContext`; that is different from an uploaded binary attachment. For generic non-text files, ACP resource links can identify a path, but clients must not assume the bridge can dereference it or the model can interpret the MIME type.

## Unsupported today / unknowns

1. No image picker, file picker, drag/drop, preview/removal UI, attachment metadata, persistence link to ledger events, or attachment propagation on handoff exists in the current Swift/FFI/session path.
2. No dynamic ACP capability negotiation is used to choose or gate a structured prompt. `initialize` reads only `protocolVersion`; image/embedded-context capability values are not retained. The mock bridge explicitly advertises `image: false`.
3. No universal support for Office formats, archives, audio/video, arbitrary binaries, remote URLs, or OCR/text extraction can be inferred from `resource_link`. These require explicit behavior per bridge/provider.
4. No documented Chorus-specific max file size, count, pixel limit, total request bound, MIME allowlist, or cleanup policy exists. The blob store's compression and garbage collection are not attachment retention/deletion semantics.
5. Before implementation, probe/pin supported bridge versions and confirm how each maps ACP `image` and `resource` blocks, attachment ordering, multimodal model selection, and errors. At runtime, gate by the live ACP capability handshake and surface unsupported model/format/size errors before sending; preserve original blobs in Chorus while allowing normalized provider payloads.
